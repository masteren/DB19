## 一、トランザクション

トランザクションとは、データベースで**ひとまとまりとして実行される一連の処理**のこと。すべて成功する（COMMIT）か、すべて取り消される（ROLLBACK）かのどちらかになる。

授業ノート三行の対応：

- **DBMS がトランザクションを制御** —— スケジューリング・コミット・ロールバックは DBMS が一括管理し、アプリ側は「開始／コミット／ロールバック」を宣言するだけ。
- **処理中に中断されない** —— **原子性**に対応：「途中までやった」状態のままにはならない。
- **他の処理が割り込まれない** —— **独立性（隔離性）**に対応：並行処理中、他のトランザクションの未確定な途中状態は見えない。

### ACID 4特性

| 特性 | 日本語 | 内容 |
|------|------|------|
| Atomicity | 原子性 | 全部やるか、全部やらないか |
| Consistency | 一貫性 | トランザクションの前後で制約を満たす（例：残高がマイナスにならない） |
| Isolation | 独立性／隔離性 | 並行するトランザクション同士が互いに干渉しない |
| Durability | 持続性 | 一度 COMMIT したら、障害が起きてもデータは失われない |

### 典型的な書き方

```sql
BEGIN;              -- トランザクション開始
UPDATE 口座 SET 残高 = 残高 - 100 WHERE id = 'A';
UPDATE 口座 SET 残高 = 残高 + 100 WHERE id = 'B';
COMMIT;             -- コミット；途中でエラーなら ROLLBACK
```

振込の例：出金は成功したが入金が失敗した場合、原子性によりトランザクション全体がロールバックされ、お金が消えることはない。

## 二、ロック —— 独立性を実現する手段

複数のトランザクションが同じデータに同時にアクセスすると、制御しなければ様々な不整合（並行異常）が起きる。ロックは、トランザクションがデータにアクセスする際にそれを「押さえ」、他のトランザクションをルールに従って待たせる仕組み。

ロックには**独立した2つの軸**があり、自由に組み合わせられる。

### 軸1：ロックの粒度（何に対してロックするか）

- **行ロック（Row Lock）** —— 操作対象の行だけをロックする。粒度が細かく並行度が高い一方、ロック数が多くなり管理コストが上がる。
- **表ロック（Table Lock）** —— テーブル全体をロックする。粒度が粗く管理コストは低いが、並行度が下がる。

> 原則：**粒度が細かいほど → 並行性は良くなるが、管理コストは上がる**。
> MySQL InnoDB はデフォルトで行ロックを使い、全表 DDL のような特定の場面でのみ表ロックに格上げされる。

### 軸2：ロックのモード（どうロックするか）

- **共有ロック（Shared Lock、S ロック）** —— 「読み取りロック」。同じデータに対して複数のトランザクションが同時に S ロックを持てる（読み取り同士は競合しない）。保持中は他者も読めるが変更はできない。
- **排他ロック（Exclusive Lock、X ロック）** —— 「書き込みロック」。データを変更する際に取得し、そのデータを**独占**する。他のトランザクションは読むことも書くこともできない。

#### ロック互換表

| 要求 ↓ ＼ 既存 → | 共有ロック S | 排他ロック X |
|------|------|------|
| **共有ロック S** | ✅ 互換 | ❌ 待機 |
| **排他ロック X** | ❌ 待機 | ❌ 待機 |

> 一言でいうと：**「読み＋読み」だけが共存でき、どちらかが書き込みなら必ず待たされる。**

## 三、デッドロック

ロックがある以上、デッドロックは起こりうる：トランザクション A は X をロックして Y を欲しがり、トランザクション B は Y をロックして X を欲しがる、という互いに待ち合う状態。

```
トランザクションA: Xをロック ──待機──> Y
                                ↑ ↓
トランザクションB: Yをロック ──待機──> X
```

**DBMS はデッドロックを検知すると、いずれかのトランザクションを強制的にロールバックする（victim／犠牲者）**ことで、もう一方を継続させる。

アプリ側の対策：

- 資源への一定の順序でのアクセス
- トランザクションの持続時間を短くする
- タイムアウトを設定する

---

## 四、分離レベル

ロックは仕組みであり、分離レベルは選択可能な「隔離の強さ」である。レベルが高いほどロックが厳しくなり、一貫性は良くなるが並行性は下がる。

| 分離レベル | 防げる異常 |
|---------|------------|
| READ UNCOMMITTED | （ほぼ防げない） |
| READ COMMITTED | ダーティリード |
| REPEATABLE READ | ダーティリード＋反復不能読み取り |
| SERIALIZABLE | すべて（ファントムリードを含む） |

### 3種類の並行異常

- **ダーティリード（Dirty Read）**：他者の**未コミット**のデータを読んでしまい、相手がロールバックすると読んだ内容が無駄になる。
- **反復不能読み取り（Non-repeatable Read）**：同一トランザクション内で同じ行を2回読むと、値が変わっている（他者が変更してコミットしたため）。
- **ファントムリード（Phantom Read）**：同じ条件のクエリを2回実行すると、**件数**が変わっている（他者が該当する行を挿入／削除したため）。

---

## 五、全体の論理のつながり（一言でまとめると）

**トランザクションの独立性** → **ロック**で保証する → ロックは「粒度（行／表）」と「モード（S／X）」の2軸に分かれる → 組み合わせ方を誤ると**デッドロック**が起きる → 上位層で**分離レベル**を使って厳しさを統一管理する

## 六、実機検証（XAMPP + MySQL、empdb.employees）

授業のロック確認プリント「DB22 トランザクション（ロック）確認方法１」に沿って、コマンドプロンプト2枚（Aさん／Bさん）を開き、`empdb` の `employees` テーブル（employee_id 100〜102）で実際に検証した。

### 確認2：ROLLBACK

Aさんが `BEGIN` → `UPDATE`（salary+9999）で仮更新している間、Bさんが同じ行を SELECT しても値は変わって見えない（仮更新は他者に見えない）ことを確認。その後 `ROLLBACK;` すると元の値に戻り、両者の結果が一致した。

> 教訓：`ROLLBACK;` を打っても `Query OK, 0 rows affected` が返るだけで実際には値が戻らないケースが発生した。原因は、直前の `BEGIN` が正しく効かないまま（コマンドのタイポ等）`UPDATE` が autocommit で即座にコミットされてしまっていたため。ROLLBACK は「今開いているトランザクション内の変更」しか戻せず、すでにコミット済みのものは戻せない。

### 確認3：COMMIT とロック待ち

Aさんが `BEGIN` → `UPDATE`（未COMMIT）の状態で、Bさんが同じ行を `UPDATE` しようとすると処理が止まり（Waiting）、既定のタイムアウト後に

```
ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction
```

が発生した。Aさんが `COMMIT;` した後、Bさんが SELECT すると、Aさんがコミットした値が見えるようになった。Bさん自身の UPDATE は失敗しているため、値は上書きされない。

### 確認4：明示的なロック（`SELECT ... FOR UPDATE`）

`UPDATE` を使わなくても、`SELECT ... FOR UPDATE;` だけで対象行に排他ロックをかけられることを確認。Aさんがこれで行をロックしている間、Bさんの `UPDATE` は確認3と同様にロック待ち→タイムアウトになった。ロックは行を「押さえている」ことが本質で、実際にデータを書き換えたかどうかは関係ない。

### まとめ

| 確認 | Aさんの操作 | Bさんへの影響 |
|------|------------|--------------|
| 確認2 | BEGIN→UPDATE→ROLLBACK | 仮更新中は見えない／ROLLBACK後は元の値 |
| 確認3 | BEGIN→UPDATE→COMMIT | UPDATEしようとするとロック待ち→タイムアウト、COMMIT後は新しい値が見える |
| 確認4 | BEGIN→SELECT FOR UPDATE→COMMIT | UPDATEしようとするとロック待ち→タイムアウト（データ自体は変わらない） |

### 確認5：デッドロック（`t_bank` テーブル）

「DB22 トランザクション（ロック）確認方法２」に沿って、送金の往復パターンでデッドロックを再現した。

準備データ：

```sql
CREATE TABLE t_bank(f_id int(3), f_Name varchar(20), f_amount int(8), primary key(f_id));
INSERT INTO t_bank VALUES(1,'My_BK',5000);
INSERT INTO t_bank VALUES(99,'Mom_BK',8880000);
```

シナリオ：Aさん（母）は f_id=99 から引いて f_id=1 に振り込む、Bさん（私）は f_id=1 から引いて f_id=99 に振り込む――**更新の順序が互いに逆**になっている。

1. A：`BEGIN;` → `f_id=99` を更新（未確定、ロック取得）
2. B：`BEGIN;` → `f_id=1` を更新（未確定、ロック取得）— ここまでは互いに別の行なので競合しない
3. A：続けて `f_id=1` を更新しようとして、Bのロック待ちで Waiting
4. B：続けて `f_id=99` を更新しようとした瞬間、循環待ちが成立しMySQLが即座にデッドロックを検出：

```
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

Bのトランザクションはこのエラーで**自動的に全体がROLLBACK**され（自分でROLLBACKを打つ必要はない）、Bの更新は一切反映されなかった。一方Aは待ちが解除されて更新が成功し、`COMMIT;` して確定。

最終結果（実機で確認）：

```
f_id | f_Name | f_amount
1    | My_BK  | 55000     -- 5000 + Aが振り込んだ50000
99   | Mom_BK | 8830000   -- 8880000 − Aが引き出した50000
```

Bが引き出そうとした3000はどこにも反映されておらず、デッドロックで負けた側（victim）のトランザクションが丸ごと消えることを実機で確認できた。
