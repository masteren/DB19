# 2026-05-26 数据库设计笔记

## 中文

本周继续学习数据库设计，重点从 ER 图进入表设计。课堂内容说明了实体和属性如何转换为关系数据库中的表和字段，以及在表设计阶段需要考虑主键、唯一约束、非空约束、外键和命名规则。

### 从 ER 图到表设计

ER 图整理的是业务中的实体、属性和关系。表设计则需要把这些内容转换成数据库可以实际创建和使用的结构。

1. 实体转换为表
   - ER 图中的一个实体通常对应数据库中的一张表。
   - 例：コース实体可以转换为コース表。
   - 表名要能清楚表示管理对象，企业项目中通常会按照统一命名规则决定表名。

2. 属性转换为字段
   - 实体拥有的属性会成为表中的字段。
   - 例：コースコード、コース名、開催期間等属性可以成为コース表的字段。
   - 字段名需要保持统一，例如使用半角英数字、下划线，避免混乱的命名方式。

3. 主键设计
   - 主键用于唯一识别表中的一条记录。
   - 主键字段不能重复，也不能为 NULL。
   - 如果单个字段不能唯一识别记录，可以使用复合主键。

4. 外键设计
   - 外键用于表示表和表之间的关系。
   - 外键字段引用其他表的主键，保证数据之间的对应关系正确。
   - 例：スケジュール表中的コースコード可以作为外键连接コース表。

### 约束条件

表设计时不仅要决定字段，还需要决定字段的规则。

| 约束 | 作用 |
| --- | --- |
| PRIMARY KEY | 主键，唯一识别记录 |
| UNIQUE | 不允许重复值 |
| NOT NULL | 必须输入值 |
| FOREIGN KEY | 引用其他表的主键 |

这些约束可以防止错误数据进入数据库。例如，主键可以避免重复记录，NOT NULL 可以防止重要字段为空，外键可以防止引用不存在的数据。

### 正规化和表设计

正规化是在表设计时减少重复数据、避免维护问题的重要方法。通过正规化，可以把混在一张表中的内容拆分成合适的多个表，并用主键和外键连接。

本周课堂中继续以课程相关的数据为例，说明コース、スケジュール等信息应该根据含义分开管理。コース表保存课程本身的信息，スケジュール表保存开课日期、负责讲师等实际实施信息。这样可以减少重复输入，也方便后续修改。

### 本周重点

- ER 图表示概念设计，表设计是把 ER 图转换成实际数据库结构。
- 实体通常转换为表，属性转换为字段。
- 主键用于唯一识别记录，必须唯一且不能为空。
- UNIQUE 表示字段值不能重复，但和主键的用途不同。
- NOT NULL 表示字段必须输入值。
- 外键用于连接相关表，并保证引用关系正确。
- 表名和字段名需要遵守项目的命名规则。
- 正规化可以减少重复数据，提升数据库维护性。

## 日本語

今週はデータベース設計の続きとして、ER 図からテーブル設計へ進む内容を学習しました。授業では、エンティティと属性をリレーショナルデータベースのテーブルとカラムに変換する方法、主キー、ユニーク制約、NOT NULL 制約、外部キー、命名規則について確認しました。

### ER 図からテーブル設計へ

ER 図は業務上のエンティティ、属性、リレーションシップを整理するための図です。テーブル設計では、それらを実際にデータベースで作成できる形に変換します。

1. エンティティをテーブルにする
   - ER 図の 1 つのエンティティは、通常 1 つのテーブルになる。
   - 例：コースエンティティはコーステーブルになる。
   - テーブル名は管理対象が分かる名前にし、企業プロジェクトでは命名規約に従う。

2. 属性をカラムにする
   - エンティティが持つ属性は、テーブルのカラムになる。
   - 例：コースコード、コース名、開催期間などはコーステーブルのカラムになる。
   - カラム名は半角英数字やアンダースコアなど、統一されたルールで付ける。

3. 主キーを設計する
   - 主キーはテーブル内の 1 件のレコードを一意に識別する項目である。
   - 主キーの値は重複できず、NULL にもできない。
   - 1 つのカラムで一意にできない場合は、複合主キーを使う。

4. 外部キーを設計する
   - 外部キーはテーブル同士の関係を表す項目である。
   - 外部キーは他のテーブルの主キーを参照し、データの対応関係を保つ。
   - 例：スケジュールテーブルのコースコードは、コーステーブルを参照する外部キーになる。

### 制約条件

テーブル設計では、カラムだけでなく、そのカラムにどのようなルールを持たせるかも決めます。

| 制約 | 役割 |
| --- | --- |
| PRIMARY KEY | レコードを一意に識別する |
| UNIQUE | 重複した値を入れられない |
| NOT NULL | 必ず値を入力する |
| FOREIGN KEY | 他のテーブルの主キーを参照する |

これらの制約により、誤ったデータの登録を防ぐことができます。主キーは重複データを防ぎ、NOT NULL は重要な項目の未入力を防ぎ、外部キーは存在しないデータを参照することを防ぎます。

### 正規化とテーブル設計

正規化は、テーブル設計でデータの重複を減らし、保守しやすい構造にするための考え方です。1 つの表に混ざった情報を意味ごとに分け、主キーと外部キーで関連付けます。

授業ではコース関連のデータを例に、コースとスケジュールなどを分けて管理する考え方を確認しました。コーステーブルにはコースそのものの情報を持たせ、スケジュールテーブルには開催日や担当講師などの実施情報を持たせます。これにより、同じ情報を何度も入力する必要が減り、後から修正しやすくなります。

### 今週のポイント

- ER 図は概念設計を表し、テーブル設計はそれを実際のデータベース構造に変換する作業である。
- エンティティはテーブルに、属性はカラムに変換する。
- 主キーはレコードを一意に識別し、重複と NULL を許可しない。
- UNIQUE は値の重複を禁止するが、主キーとは役割が異なる。
- NOT NULL は値の入力を必須にする。
- 外部キーは関連するテーブルをつなぎ、参照関係を正しく保つ。
- テーブル名とカラム名はプロジェクトの命名規約に従う。
- 正規化により、データの重複を減らし、保守性を高められる。

## English

This week continued database design by moving from ER diagrams to table design. The class covered how to convert entities and attributes into relational database tables and columns, and how to think about primary keys, unique constraints, NOT NULL constraints, foreign keys, and naming rules.

### From ER Diagram to Table Design

An ER diagram organizes business entities, attributes, and relationships. Table design converts that model into structures that can actually be created and used in a database.

1. Convert entities into tables.
   - One entity in an ER diagram usually becomes one table.
   - Example: the course entity becomes a course table.
   - Table names should clearly describe the managed object and follow project naming rules.

2. Convert attributes into columns.
   - Attributes of an entity become columns in the table.
   - Example: course code, course name, and course period become columns in the course table.
   - Column names should follow consistent rules, such as using half-width alphanumeric characters and underscores.

3. Design primary keys.
   - A primary key uniquely identifies one record in a table.
   - Primary key values cannot be duplicated and cannot be NULL.
   - If one column is not enough to identify a record, a composite primary key can be used.

4. Design foreign keys.
   - A foreign key represents a relationship between tables.
   - A foreign key references the primary key of another table and keeps related data consistent.
   - Example: the course code in the schedule table can reference the course table.

### Constraints

Table design also defines rules for each column.

| Constraint | Purpose |
| --- | --- |
| PRIMARY KEY | Uniquely identifies a record |
| UNIQUE | Prevents duplicate values |
| NOT NULL | Requires a value |
| FOREIGN KEY | References a primary key in another table |

These constraints prevent invalid data from being stored. A primary key prevents duplicate records, NOT NULL prevents required fields from being empty, and a foreign key prevents references to records that do not exist.

### Normalization and Table Design

Normalization is an important method for reducing duplicated data and avoiding maintenance problems. It separates mixed information into appropriate tables and connects them with primary keys and foreign keys.

The class used course-related data as an example. Course information and schedule information should be managed separately. The course table stores information about the course itself, while the schedule table stores implementation details such as date and assigned teacher. This reduces repeated input and makes later changes easier.

### Key Points

- An ER diagram represents conceptual design, while table design converts it into an actual database structure.
- Entities usually become tables, and attributes become columns.
- A primary key uniquely identifies records and cannot be duplicated or NULL.
- UNIQUE prevents duplicate values, but it has a different role from a primary key.
- NOT NULL requires a value.
- A foreign key connects related tables and keeps references valid.
- Table and column names should follow project naming rules.
- Normalization reduces duplicated data and improves maintainability.
