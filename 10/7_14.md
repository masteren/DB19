# 2026-07-14 数据库课堂笔记（结合・INDEX・VIEW）

## 中文

本周内容围绕四个主题：表连接（JOIN）、数据库设计流程复习、索引（INDEX）和视图（VIEW）。

### 1. 表连接（JOIN）

学习使用多个表的目的：正规化之后，数据被拆分到多张表中，实际业务查询往往需要把这些表重新组合起来。JOIN 就是把多张表按照主键和外键的对应关系拼接成一个结果集的操作。

以教育管理系统为例，受講申し込み表只保存受講者ID和コースコード，要显示受講者的姓名和课程名称，就需要连接受講者表和コース表：

```sql
SELECT s.氏名, c.コース名, m.実施日
FROM 受講申し込み m
JOIN 受講者 s ON m.受講者ID = s.受講者ID
JOIN コース c ON m.コースコード = c.コースコード;
```

主要连接方式：

| 连接方式 | 说明 |
| --- | --- |
| 内部结合（INNER JOIN） | 只返回两张表中都能匹配到的行 |
| 外部结合（LEFT JOIN） | 左表的所有行都返回，右表没有匹配时补 NULL |
| 自连接 | 同一张表和自己连接，例如员工表中查找上司 |

要点：

- 连接条件写在 `ON` 里，通常是「外键 = 被引用表的主键」。
- 正规化把数据拆开，JOIN 把数据按需要重新组合，两者是配套的。
- 忘记写连接条件会产生笛卡尔积（所有行两两组合），结果行数会爆炸。

### 2. 设计流程复习

数据库设计的两个核心步骤：

1. **ER 图作成**：从业务中抽取实体、属性和关系，确定主键、外键和基数。
2. **表设计**：把 ER 图转换为具体的表结构，确定字段、数据类型和约束（主键、NOT NULL、UNIQUE、外键）。

设计做好之后才进入实装（CREATE TABLE），这也是本学期从第 2 周到第 8 周走过的完整流程。

### 3. INDEX（索引）

索引是为了从大量数据中高速检索而使用的机制，类似书的目录：不用从第一页翻到最后一页，而是先查目录再直接跳到对应位置。

要点：

1. **用途**：加快 `WHERE` 条件查询和 JOIN 的匹配速度。数据量越大，效果越明显。
2. **代价**：INSERT / UPDATE / DELETE 时索引也要跟着更新，会消耗 CPU 和内存，更新变慢。所以索引不是越多越好，只给经常用于检索的列建索引。
3. **主键自动带索引**：定义 PRIMARY KEY 时，数据库会自动为主键列创建索引，不需要手动再建。

创建和删除索引的语法：

```sql
-- 为受講者表的氏名列创建索引
CREATE INDEX idx_受講者_氏名 ON 受講者 (氏名);

-- 删除索引
DROP INDEX idx_受講者_氏名 ON 受講者;
```

适合建索引的列：经常出现在 `WHERE`、`JOIN ... ON`、`ORDER BY` 中的列。不适合的情况：表很小、列的取值种类很少（例如性别）、频繁更新的列。

### 4. VIEW（视图）

视图是**虚拟的表**：它本身不保存数据（没有实体），只保存一条 SELECT 语句。查询视图时，数据库实时执行这条 SELECT，从原表取数据。

视图体现的是**利用者视点**：底层表按照正规化的结构设计，而视图可以按照使用者习惯的形式来呈现数据。

```sql
-- 创建视图：受講一覧（把 3 张表的 JOIN 封装起来）
CREATE VIEW 受講一覧 AS
SELECT s.受講者ID, s.氏名, c.コース名, m.実施日
FROM 受講申し込み m
JOIN 受講者 s ON m.受講者ID = s.受講者ID
JOIN コース c ON m.コースコード = c.コースコード;

-- 之后像普通表一样查询即可
SELECT * FROM 受講一覧 WHERE 氏名 = '秋元 正則';

-- 删除视图
DROP VIEW 受講一覧;
```

#### VIEW 的优点

1. **不用每次写复杂 SQL**：把常用的多表 JOIN、复杂条件封装成视图，之后用简单的 `SELECT * FROM 视图名` 就能查询。
2. **安全性**：可以只把需要的列放进视图，向使用者隐藏敏感列（例如講師表的緊急連絡先），只授予视图的查询权限，不开放原表。

注意点：

- 视图不保存数据，原表数据变了，视图查询结果也跟着变。
- 视图本质上是「起了名字的 SELECT 语句」，多层嵌套视图可能影响性能。

### 本周重点

- 正规化拆表，JOIN 合表：两者配合才能既保证数据一致性又满足查询需求。
- INDEX 用空间和更新成本换检索速度；主键自动有索引。
- VIEW 是没有实体的虚拟表，优点是简化复杂 SQL 和控制访问权限。

## 日本語

今週は、テーブル結合（JOIN）、データベース設計の流れの復習、インデックス（INDEX）、ビュー（VIEW）の 4 つのテーマを学習しました。

### 1. テーブル結合（JOIN）

複数テーブルを扱う目的：正規化によってデータは複数のテーブルに分割されるが、実際の業務の問い合わせでは、それらを組み合わせて表示する必要がある。JOIN は主キーと外部キーの対応関係に基づいて、複数のテーブルを 1 つの結果セットにつなげる操作である。

教育管理システムを例にすると、受講申し込みテーブルには受講者IDとコースコードしかないため、氏名やコース名を表示するには受講者テーブルとコーステーブルを結合する必要がある：

```sql
SELECT s.氏名, c.コース名, m.実施日
FROM 受講申し込み m
JOIN 受講者 s ON m.受講者ID = s.受講者ID
JOIN コース c ON m.コースコード = c.コースコード;
```

主な結合の種類：

| 結合の種類 | 説明 |
| --- | --- |
| 内部結合（INNER JOIN） | 両方のテーブルで一致した行だけを返す |
| 外部結合（LEFT JOIN） | 左テーブルの全行を返し、一致しない部分は NULL になる |
| 自己結合 | 同じテーブル同士を結合する。例：社員テーブルで上司を調べる |

ポイント：

- 結合条件は `ON` に書く。通常は「外部キー = 参照先の主キー」。
- 正規化はデータを分割し、JOIN は必要に応じて再び組み合わせる。両者はセットの関係にある。
- 結合条件を書き忘れると直積（全行同士の組み合わせ）になり、行数が爆発する。

### 2. 設計の流れの復習

データベース設計の 2 つの中心ステップ：

1. **ER 図作成**：業務からエンティティ・属性・リレーションシップを抽出し、主キー・外部キー・カーディナリティを決める。
2. **テーブル設計**：ER 図を具体的なテーブル構造に変換し、カラム・データ型・制約（主キー、NOT NULL、UNIQUE、外部キー）を決める。

設計が完成してから実装（CREATE TABLE）へ進む。これは第 2 週から第 8 週まで学んできた一連の流れである。

### 3. INDEX（索引）

インデックスは、大量のデータから高速にデータを検索するための仕組みで、本の目次に似ている。最初のページから順に探すのではなく、目次を見て目的の位置へ直接ジャンプするイメージ。

ポイント：

1. **用途**：`WHERE` 条件の検索や JOIN の照合を高速化する。データ量が多いほど効果が大きい。
2. **コスト**：INSERT / UPDATE / DELETE の際にインデックスも更新する必要があるため、CPU・メモリに負荷がかかり、更新が遅くなる。インデックスは多ければ良いわけではなく、検索によく使う列だけに作る。
3. **主キーは自動的に INDEX を持つ**：PRIMARY KEY を定義すると、データベースが自動的にインデックスを作成するため、手動で作る必要はない。

インデックスの作成と削除：

```sql
-- 受講者テーブルの氏名列にインデックスを作成
CREATE INDEX idx_受講者_氏名 ON 受講者 (氏名);

-- インデックスの削除
DROP INDEX idx_受講者_氏名 ON 受講者;
```

インデックスに向く列：`WHERE`、`JOIN ... ON`、`ORDER BY` によく使う列。向かない場合：テーブルが小さい、値の種類が少ない列（例：性別）、更新が頻繁な列。

### 4. VIEW（ビュー）

ビューは**仮想の表**である。データそのものは保存せず（実体がない）、SELECT 文だけを保存する。ビューを参照すると、データベースがその SELECT 文を実行して元のテーブルからデータを取り出す。

ビューは**利用者視点**の仕組みである。元のテーブルは正規化された構造で設計されているが、ビューを使えば利用者にとって分かりやすい形でデータを見せられる。

```sql
-- ビューの作成：受講一覧（3 テーブルの JOIN をまとめる）
CREATE VIEW 受講一覧 AS
SELECT s.受講者ID, s.氏名, c.コース名, m.実施日
FROM 受講申し込み m
JOIN 受講者 s ON m.受講者ID = s.受講者ID
JOIN コース c ON m.コースコード = c.コースコード;

-- 以降は普通のテーブルのように問い合わせできる
SELECT * FROM 受講一覧 WHERE 氏名 = '秋元 正則';

-- ビューの削除
DROP VIEW 受講一覧;
```

#### VIEW の利点

1. **複雑な SQL を毎回記述しなくて良い**：よく使う複数テーブルの JOIN や複雑な条件をビューにまとめておけば、以降は `SELECT * FROM ビュー名` だけで問い合わせできる。
2. **セキュリティの点**：必要な列だけをビューに含めることで、機密性の高い列（例：講師テーブルの緊急連絡先）を利用者から隠せる。元のテーブルへの権限を与えず、ビューの参照権限だけを与える運用ができる。

注意点：

- ビューはデータを持たないため、元のテーブルのデータが変わると、ビューの結果も変わる。
- ビューは「名前を付けた SELECT 文」であり、多段のビューの入れ子は性能に影響することがある。

### 今週のポイント

- 正規化でテーブルを分割し、JOIN で組み合わせる。両方そろって、データの整合性と問い合わせの利便性が両立する。
- INDEX は更新コストと引き換えに検索を高速化する。主キーは自動的にインデックスを持つ。
- VIEW は実体のない仮想の表で、複雑な SQL の簡略化とアクセス制御に役立つ。

## English

This week covered four topics: table joins (JOIN), a review of the database design workflow, indexes (INDEX), and views (VIEW).

### 1. Table Joins (JOIN)

Why we work with multiple tables: after normalization, data is split across several tables, but real business queries usually need to recombine them. A JOIN connects multiple tables into one result set based on the primary key / foreign key relationships.

In the education management system example, the enrollment table stores only the student ID and course code, so displaying student names and course names requires joining the student and course tables:

```sql
SELECT s.氏名, c.コース名, m.実施日
FROM 受講申し込み m
JOIN 受講者 s ON m.受講者ID = s.受講者ID
JOIN コース c ON m.コースコード = c.コースコード;
```

Main join types:

| Join type | Description |
| --- | --- |
| Inner join (INNER JOIN) | Returns only rows that match in both tables |
| Outer join (LEFT JOIN) | Returns all rows from the left table; unmatched columns become NULL |
| Self join | Joins a table with itself, e.g. finding an employee's manager |

Key points:

- The join condition goes in `ON`, usually "foreign key = referenced table's primary key".
- Normalization splits data apart; JOIN recombines it as needed. They work as a pair.
- Forgetting the join condition produces a Cartesian product (every row combined with every row), and the row count explodes.

### 2. Design Workflow Review

The two core steps of database design:

1. **ER diagram creation**: extract entities, attributes, and relationships from the business, then decide primary keys, foreign keys, and cardinality.
2. **Table design**: convert the ER diagram into concrete table structures with columns, data types, and constraints (primary key, NOT NULL, UNIQUE, foreign key).

Implementation (CREATE TABLE) comes only after the design is complete — this is the full workflow we followed from week 2 to week 8.

### 3. INDEX

An index is a mechanism for finding data quickly in a large table, similar to a book's table of contents: instead of scanning from the first page, you look up the location and jump straight to it.

Key points:

1. **Purpose**: speeds up `WHERE` filtering and JOIN matching. The larger the data, the bigger the benefit.
2. **Cost**: every INSERT / UPDATE / DELETE must also update the index, which consumes CPU and memory and slows down writes. More indexes are not always better — create them only on columns frequently used for searching.
3. **Primary keys are indexed automatically**: defining a PRIMARY KEY makes the database create an index on it, so there is no need to add one manually.

Creating and dropping an index:

```sql
-- Create an index on the student name column
CREATE INDEX idx_受講者_氏名 ON 受講者 (氏名);

-- Drop the index
DROP INDEX idx_受講者_氏名 ON 受講者;
```

Good candidates for indexes: columns frequently used in `WHERE`, `JOIN ... ON`, and `ORDER BY`. Poor candidates: small tables, low-cardinality columns (e.g. gender), and frequently updated columns.

### 4. VIEW

A view is a **virtual table**: it stores no data of its own (it has no physical body), only a SELECT statement. When you query a view, the database runs that SELECT against the underlying tables in real time.

A view represents the **user's perspective**: the underlying tables follow the normalized design, while the view presents the data in a form that is convenient for the user.

```sql
-- Create a view that wraps a 3-table JOIN
CREATE VIEW 受講一覧 AS
SELECT s.受講者ID, s.氏名, c.コース名, m.実施日
FROM 受講申し込み m
JOIN 受講者 s ON m.受講者ID = s.受講者ID
JOIN コース c ON m.コースコード = c.コースコード;

-- Query it like a normal table
SELECT * FROM 受講一覧 WHERE 氏名 = '秋元 正則';

-- Drop the view
DROP VIEW 受講一覧;
```

#### Benefits of views

1. **No need to rewrite complex SQL every time**: wrap frequently used multi-table JOINs and complex conditions in a view, then simply run `SELECT * FROM view_name`.
2. **Security**: include only the necessary columns in the view to hide sensitive columns (e.g. the instructor's emergency contact) from users. Grant access to the view only, not to the underlying tables.

Notes:

- A view holds no data, so when the underlying tables change, the view's results change too.
- A view is essentially a "named SELECT statement"; deeply nested views can hurt performance.

### Key Points

- Normalization splits tables; JOIN recombines them. Together they provide both data consistency and query convenience.
- An INDEX trades write cost for read speed; primary keys are indexed automatically.
- A VIEW is a virtual table with no physical data, useful for simplifying complex SQL and controlling access.
